## 1. Context

ADR 0002 made Synapse the primary source control system for AI agents, with Git as a small machine bridge, and fixed the performance rule (section 2.6). It left the native model to this ADR. The owner's direction, verbatim (Drake, 2026-10-14):

> "I want Synapse to be the new Git for AI."
> "Don't just copy features because we feel like we need them. I want you to take the good parts of everything and make the best system possible."
> "This is going to be for AI only. AI is going to be the only one writing code in the future and this is not going to be for humans. Nothing human-related needs to be in this."
> "Eventually Synapse will take over Git from our actual hardware."
> "Be inventive... Build your own."
> "When you're doing things to improve speed, I don't want '5 times faster' or '32 agents'. The ultimate goal is to be as close to physically possible in speed and throughput. If there's something between speed and the hard metal, it needs to get rewritten or reworked to make it faster. We need to push this to the limit."
> "I want our things to be measured in physical scientific units that can be measured and verified in a scientifically verifiable open way. I do not want people to be hiding behind these fake units, like tokens or even bytes."
> "Omega needs to be the final layer that is just talking to the metal, the machine itself."
> "Fuck the targets. Chase the boundaries of physical limitation."

This ADR derives what AI agents need from evidence (section 3), judges the best ideas from other systems against those needs (section 4), and defines the native model (section 5), the performance method (section 6), a Turing-unit proposal (section 7), the crate map (section 8), and the implementation sequence (section 9).

## 2. Principles

* **P1. AI only.** Every reader and writer is an agent or a machine. Nothing exists for a human to read: no prose messages, no review pages, no display formats, no human branch names.
* **P2. Need first.** Every element in section 5 names the need it serves (N1 to N15, section 3). An idea from another system is adopted only for a named need. Copying a feature without a need is not allowed.
* **P3. The physical bound is the only goal (first-class).** Performance is stated in SI units only: seconds per accepted change (with the latency distribution), joules per accepted change, and watts. Each result is reported next to a physical bound for the same work, with the bound's derivation and the source of every input, and as the fraction of that bound achieved (bound divided by measured, at most 1). There are no targets, no multipliers, no operations-per-second headlines, no token counts, and no byte counts as performance measures; amounts of data are supporting facts only. Every layer between an agent and the metal (process spawns, text and JSON formats, per-file filesystem objects, kernel copies, locks, allocations, the filesystem itself) must justify its measured cost in seconds and joules or be removed. Measurements are open and reproducible: the instrument, its resolution, the sampling method, the host load, the commands, and the raw samples are published with checksums. This extends ADR 0002 section 2.6; section 6 makes it operational.
* **P4. Evidence over assertion.** A claim about a change (it builds, it passes, it is equivalent) counts only as a signed receipt bound to the exact content it was measured on. Fail closed everywhere (unchanged from ADR 0001).
* **P5. Language-neutral formats; Omega is the destination.** Rust is scaffolding and Omega is the destination (aien-architecture ADR 0024, as recorded in the mind map note `no-rust-atlas-lineage-conflict`). Every persisted and wire format is a fixed-width, little-endian, length-prefixed binary specification with no Rust-specific serialization, so that an Omega implementation on AIENOS can read the same bytes. The Rust crates are the current implementation and the specification-by-test for that port.
* **P6. Never lose work.** Nothing an agent produced is destroyed by another agent's action. Rewrites, undo, and discard are recorded, and only garbage collection under explicit retention rules frees space. Retention is per owner (section 5.9), so no agent's write volume can shorten another agent's retention. The one exception is audited cryptographic erasure of a leaked secret (section 5.13), which needs the delegate threshold and leaves a permanent record that the erasure happened.

## 5. The Synapse Native Model

### 5.1 Objects and identity (N1, N4, N12)

Every object is immutable and content-addressed with a domain-separated SHA-256 digest (the existing scheme in `docs/SCHEMA_AND_CONSISTENCY.md`), each with its own type so no identity can be substituted for another (ADR 0001 section 2.3). The hash function is reviewed by experiment X1 (section 6.4).

| Identity | What it names | Notes |
| :--- | :--- | :--- |
| `BlobDigest` (kept) | File content bytes | Digest of the whole content, independent of chunking, so chunk parameters can change without changing identity |
| `ChunkDigest` (new) | One content-defined chunk of a large blob | Storage and transfer unit only (section 5.9) |
| `TreeDigest` (new) | A whole repository state as a Merkle tree of directories | Native encoding, not Git's; Git tree IDs are computed only at the bridge. Evidence binds to this |
| `ChangeId` (new) | One unit of intended work across all its rewrites and retries | 16 random bytes, not content-derived because content changes on rewrite. A `ChangeId` is bound to its **creating chain**: the delegation chain of the key whose admission first used it, recorded in that first admission witness. Adding a revision under an existing `ChangeId` (joining) is accepted only from a key whose chain descends from the creating chain, or from a key whose grant names that `ChangeId` in its change scope (section 5.8); anything else is refused with a typed refusal, which covers both an accidental collision and an attempt to hijack another task. An orchestrator creates the `ChangeId` and its workers, whose grants descend from it, add their attempts. Several live revisions of one `ChangeId` are divergent attempts; selecting one prunes the others with obsolescence markers, and pruning needs a chain that is the creating chain or dominates it |
| `ChangesetId` (kept, redefined in envelope v2) | One immutable revision of a change | Digest of the revision's content only: `ChangeId`, parent revisions or base `TreeDigest`, mutations, conflict terms, and the intent record. It excludes who submitted it and when. v1 envelopes keep their v1 identities |
| `AdmissionWitness` (new) | The first admission of a revision | Recorded once by the server and never changed: `repo_id`, the submitting agent's DID and its signature over the envelope, the `IdempotencyKey`, the admission `WalSeq`, and the server's admission time. Idempotency is keyed on (`repo_id`, agent DID, `IdempotencyKey`). Replay order is the admission `WalSeq`; retention follows the owner rules of section 5.9 and the server's clock, never a client clock. For a server-derived revision the witness holds the server's machine-key signature and the digest of its `DerivationAttestation` instead of an agent signature |
| `DerivationAttestation` (new) | A revision the server produced rather than an agent: an automatic rebase, a promotion-queue merge, or a derived-file output | Signed by the server's machine key, which is listed in the repository identity document. Names the input revisions or trees, the rule applied (rebase, merge tier and canonical merge order, or the `ActionDigest` of a derived-file action), and the output `ChangesetId` and `TreeDigest`. Every rule is deterministic, so any replica can recompute the output from the named inputs and refuse an attestation that does not match. The input revisions keep their own agent signatures and attestations |
| `AuthorshipAttestation` (new) | A signed statement that an agent produced a revision, at a time | Identical content submitted under the same `ChangeId` (for example by two attempts of one task) is one revision with two attestations, so duplicate speculative attempts collapse (N1). Identical trees under different `ChangeId`s share evidence through `TreeDigest` (section 5.5). An attestation added later never revokes a receipt already accepted |
| `OperationId` (new) | One entry in the operation log (section 5.4) | Equal to the WAL frame digest that carries it |
| `ActionDigest` (new) | One exact evaluation: input root, toolchain digest, command digest, environment digest, platform | Evidence key (section 5.5). The input root is a composite: a Merkle root over sorted (`repo_id`, `TreeDigest`) pairs. A single-repository action is the one-pair case; an action that builds `omega` against `physics` names both trees, so one receipt can test them together (N13) |
| `GitOid` (kept, bridge only) | Git objects imported or exported | Never a native base; the envelope v1 field `base_git_oid` becomes a native base in v2 |

### 5.2 Intent as data, not prose (N8, N4)

The free-text `intent_summary` is replaced by an `IntentRecord`:

* `kind`: a closed enumeration (`Fix`, `Feature`, `Refactor`, `Revert`, `Merge`, `ResolveConflict`, `Format`, `DependencyUpdate`, `Generated`).
* `task`: a typed reference to the work item (tracker issue, ledger lane), never free text.
* `claims`: machine-checkable assertions the change makes, each naming a predicate type: for example "action A passes on the resulting tree", "public interface of module M is unchanged", "behaviour unchanged" for `Refactor` (discharged by an equivalence or test receipt), "reverts revision R exactly".
* `footprint`: the declared paths (later, symbols) the change intends to touch. It must lie inside the submitter's `Propose` scope, and every actual mutation must lie inside it (refused otherwise). Predictions and subscriptions use footprints; conflict detection and capability checks use the actual mutations.
* `supersedes`: revisions this one replaces (also expressed as obsolescence markers).
* `context`: an optional digest of a machine-readable rationale blob (the agent's plan or trace) for other agents. It is never part of any decision rule.

Claims are obligations: promotion requires every claim to be discharged by a passing receipt (section 5.5). A change that claims nothing beyond "passes the repository's required actions" is valid. Verification and benchmark lanes do not create revisions; they produce `EvidenceReceipt`s against existing trees, so they need no intent kind.

### 5.3 Revision states and the change algebra (N5, N12)

**States.** `Private` (visible only to its owner's delegation chain: the key that submitted it and the keys its grant descends from; N14) or `Draft` (visible within `Read` scope), then `Proposed`, then `Verified` (all claims and required actions discharged on its exact tree), then `Canonical` (promoted by quorum, immutable). The grant sets the default between `Private` and `Draft`. Revisions never change state backwards; replacing one creates a new revision and an obsolescence marker.

**Commutation.** The commutation promise is limited to T0: revisions on the same base whose actual mutations touch disjoint paths (and no file and directory prefix collision) give the same `TreeDigest` in every order, checked by a permutation test. T1 and T2 merges are not claimed to commute (three-way merging is not associative in general, and region merges can depend on order at a shared boundary). Instead, whenever more than two revisions are combined, the server merges them in canonical order (ascending `ChangesetId`) and records that order and the tier, so the result is a function of the set of revisions, never of arrival order or agent count (N12).

**Merge tiers.** The merge engine tries, in order, and records the tier used in the merged revision:

1. **T0 path:** different paths (what Synapse does today, 0.219 ms p50 per query in Gate 4).
2. **T1 region:** three-way merge of non-overlapping byte or line regions within one file. This removes the 3 over-flags of Gate 4 section 5.
3. **T2 structure:** syntax-tree merge (tree-sitter parse, GumTree matching, Spork-style merge, as Mergiraf does [S17, S18]) for languages with a grammar. A T2 result is accepted only if all of these hold, otherwise the merge falls to T3: the matched nodes edited by the two sides do not overlap; the result parses with the same grammar; and diffing the result against each side reproduces exactly the other side's edit script.
4. **T3 conflict:** a first-class conflict (below).

**Derived files.** A path can be declared derived (for example a lockfile) with the action that produces it. Derived files are never merged: after the other paths merge, the server runs the declared action on the merged tree and records its output under a `DerivationAttestation` (section 5.1), or records a conflict if the action fails. How often lockfile merges occur in AIEN repositories is UNVERIFIED.

A merged tree never inherits evidence from its parts; it must earn its own receipts (section 5.5). Policy can demand more evidence for higher tiers.

**First-class conflicts.** A tree entry can hold a `ConflictTerm`, the Jujutsu idea of a conflict as a sum of states [S7]: a set of add terms and a set of remove terms, with one more add than remove, each stored as a sorted multiset so the encoding is canonical. Each term is a full entry state: absent, or present as a file, directory, or symlink with its `FileMode` and content digest. Typed terms represent the cases Gate 4 section 5 measured: modify against delete (one term absent), file against directory (different kinds), and mode changes. Cancellation deletes an add term and a remove term only when they are identical entry states; the reduced form removes the multiset intersection of adds and removes from both sides, which is the same whatever order the cancellations happen in. One remaining add term and no remove terms is a resolved entry. Applying further changes adds terms; equal terms cancel, so rebasing twice reduces to a plain three-way conflict and reverting returns a clean tree. A tree with any conflict term can be read, rebased, and resolved, but cannot be materialized for a build and cannot be promoted. Resolution is a new revision of the same `ChangeId` with `kind = ResolveConflict`, by any agent with the capability.

**Automatic evolution, done lazily.** About 89 % of attempts are thrown away (N1), so rebasing every dependent draft when a base moves would spend most of its seconds and joules on work nobody reads, all on the single writer. Instead:

* When a base moves (canonical advances, or a parent revision is replaced), the server appends one operation that records the move. It rebases nothing at that point. Dependent drafts are found later through an index from base to dependants.
* **Reads admit nothing.** When any key with `Read` scope reads or forks a stale dependent `Private` or `Draft` revision, the server computes the rebased tree on the parallel stages (section 5.9) and returns it as a view marked derived and not admitted, cached in the bounded subtree cache. No revision, marker, or operation is written, so a reader cannot create work under a `ChangeId` it cannot join or charge anyone's quota. A fork by a non-owner starts the forker's own workspace on that computed tree, owned and paid for by the forker.
* **Only the owner chain or a proposal admits.** The rebase is admitted as a new revision of the same `ChangeId`, with an obsolescence marker and a `DerivationAttestation`, only when the revision is proposed or when a key in its creating chain (section 5.1) asks for it. The admitted revision belongs to the original revision's owner and is charged to that owner's quota and retention (section 5.9). Any conflicts are stored as terms. A draft that is never proposed or asked for is never admitted as rebased.
* Notification is targeted: a subscriber hears of a base move only if the paths the move wrote intersect its footprint (section 5.7).
* Revisions that already carry receipts (`Proposed`, `Verified`) are never rebased, so their tested trees and evidence stay intact: the promotion queue merges them onto the current head and tests the merged tree (section 5.5).
* Cost is reported, not assumed: seconds and joules per base move (the recording operation plus notification fan-out) and per lazy rebase, each against its bound (section 6).

Rebasing stops being a job agents do (the 5 rebase lanes in N5).

### 5.4 Operation log, views, and undo (N6, P6)

* Every admitted mutation (revision created, marker recorded, reference moved, receipt attached, capability granted or revoked) is one operation in the existing hash-chained WAL. An operation records the actor, the capability chain used, and the view digest before and after. When the actor is the server itself (a base-move record, a lazy rebase, a promotion merge, a derived-file output), the operation carries the server machine key's signature and, for a new revision, its `DerivationAttestation`.
* The **view** is the full set of references (canonical, workspace pointers, per-change visible heads). Its digest is a Merkle root, so two views compare in one step.
* **Undo** is a new operation that restores a chosen earlier view, either whole or filtered to one actor's operations (an orchestrator can undo one worker without touching others). Undo is itself undoable. Where a later operation by another actor conflicts with the undo, the result is recorded as conflict data, never silently dropped.
* **Who can undo what.** Undo needs a new `Undo` capability, and undoing another actor's operations needs a delegation chain that dominates that actor's (an ancestor of its grant). Undo changes references only; it never deletes objects, so content shared with other attestations or children stays (garbage collection alone frees space).
* **Facts that undo cannot reverse:** canonical promotions (canonical moves only by the promotion queue's compare-and-swap; a revert is a new change), revocations, accepted receipts, identity-document changes, final discards (section 5.9), and cryptographic erasures (section 5.13).
* **Undo survives compaction:** checkpoints keep every operation and view root inside the undo window, and the undo window is a garbage-collection root (the root rules of `docs/SCHEMA_AND_CONSISTENCY.md` section 4.1; in code these are the rules inside `checkpoint_and_compact`, and there is no `GarbageRoot` type). The undo window is per owner: an actor's operations stay undoable while that owner's retention holds (section 5.9), so another agent's write volume cannot shrink it. Undo to a view outside the window is refused with a typed refusal.
* Refused requests stay in the separate hash-chained security audit log (`synapse-auth`), bounded in size, so a flood of refusals cannot force durable writes on the hot path.

### 5.5 Evidence-carrying changes and promotion (N4, N10)

* An `EvidenceReceipt` states: the `ActionDigest` (exact input root, toolchain, command, environment, platform), the result, resources used in SI units (seconds, and joules when the instrument is present), whether the action declared all its inputs (hermetic), and the executor's machine key and signature. The shape follows in-toto (subject digests plus a typed predicate) [S23] and the Bazel Action and ActionResult split [S14].
* **The result has two parts.** The **deterministic part** is the exit status plus the digests of the outputs the action declares (built artifacts, test verdicts per test). Its digest, the result digest, is the result's identity. The **observation part** is the logs, timings, and resource figures. It is stored and served with the receipt but is never part of the result digest, because logs carry timings and differ on every run.
* **Validity rule.** A receipt applies only to the exact input root in its action. A rebase that yields the identical tree keeps its evidence for free; a different tree never inherits any. This removes the stale-PASS failure (N4) by construction.
* **Who may execute.** Executors are untrusted unless registered: only receipts from registered executor machines (machine keys listed in the repository identity document, added under the delegate threshold) running a sandbox that the requesting agent does not control count toward promotion or enter the action cache. The registered executor, not the agent, decides the hermetic flag by checking that the action read only its declared inputs. A receipt from any other executor is an observation for the agent's own use only.
* **Action cache.** Any agent asking for an action already executed on identical inputs gets the stored result. Only hermetic receipts from registered executors are reusable across machines and time. Receipts for one `ActionDigest` are compared by result digest only: a re-run with the same exit status and declared outputs but different logs agrees, and the cache keeps both observations. Receipts whose result digests differ make the cache entry a typed **`Flaky`** result that lists each distinct deterministic part and the executors that produced it. A `Flaky` entry is served as `Flaky` (useful to an agent hunting a flaky test), never as a pass, never discharges a claim, and never counts toward promotion; it leaves `Flaky` only through a new `ActionDigest` (a changed tree, toolchain, or command). A receipt is served only while its inputs and outputs are retained; garbage collection evicts it with them.
* **Independence.** A receipt does not count toward promotion if its executor shares a machine key or a delegation root with the revision's admission witness or with any attester known when the receipt was accepted (this generalizes today's `AuthSelfReviewRefused`, which compares one `author_did`). Two DIDs under one delegation root are one party. For a server-derived revision, the parties are the admitters and attesters of every input its `DerivationAttestation` names; the server's own key is never an independent executor for its own derivation.
* **Promotion queue.** Canonical advances only by compare-and-swap from the current head to a tree that (a) passed every required action and discharged every claim, on that exact tree, and (b) carries the delegate threshold of signatures. Delegates can be machines. The number of independent registered executors that must agree on each required action is repository policy, by default equal to the delegate threshold; each re-execution costs energy, so the policy and its joules per accepted change are reported together. Candidates are batched; a failed batch is bisected (bors [S24]). The merged tree the queue builds is a server-derived revision with its own `DerivationAttestation` (section 5.1) and must earn its own receipts.
* **What delegates sign.** The `ChangesetId`, the `TreeDigest`, the digest of the admission witness, and the root of the set of receipt digests the promotion relies on, so no unexamined receipt can ride along.
* **Trust root.** The quorum rule of ADR 0001 section 2.2 item 3 is unchanged. Delegates and threshold live in a Synapse identity document that mirrors the Radicle `refs/rad/id` delegates and threshold; changing it (including registering executors and the server's own machine key) needs the current threshold, as in Radicle [S11]. While the Git edge exists, the Radicle check over the bridged `GitOid` is also required, and any disagreement is refused as split-brain (existing `SplitBrainDivergence`).

### 5.6 Workspaces and speculative forks (N1, N2, N3)

* A **workspace** is a server-side pointer: a base (`TreeDigest` or revision) plus an overlay of changed paths, owned by a capability. Forking copies the pointer; it does not copy content. Every write by the agent is a draft revision (auto-snapshot), so no state lives only inside an agent.
* Reads (file, tree, diff, search) come straight from the content store. Trees are persistent Merkle structures: forks share every unchanged subtree, so memory grows with what changed, not with the number of workspaces. The cache is keyed by subtree digest and bounded (this replaces the unbounded per-changeset virtual tree cache of Gate 4 section 4).
* **Materialization for building and testing** is decided by experiment X7 among: (a) actions that read inputs by digest, with no filesystem view at all (Bazel style); (b) a lazy filesystem view that fetches on first read (CitC style [S12]); (c) a copy from the content store into memory-backed storage. The bound is the bytes the build actually reads divided by memory bandwidth.

### 5.7 Queries and subscriptions (N2, N11)

* Queries: revision, change (all revisions and markers), tree at any revision or snapshot sequence, diff as an edit script (path level now; GumTree actions [S18] at T2), content search through a trigram index over canonical trees and overlays [S25], evidence (which receipts exist for a tree; which trees passed an action), operation ranges, and conflicts.
* **Predictive conflicts:** intersect a footprint with the footprints of all open drafts, before the agent writes anything.
* **Subscriptions:** an agent subscribes to its footprint and receives every operation that touches it (at-least-once, resumable from a durable cursor, as the existing `watch` does), so it learns of overlapping work while it is still working.
* **Scope filter:** every query, search, conflict prediction, and subscription result is filtered to the caller's `Read` scope (paths and references), so a path-scoped agent learns nothing about drafts outside its scope. `Private` revisions take part only in their owner chain's predictions and are checked against others at proposal. A subscription event carries only the operation kind, the `ChangesetId`, and the written paths inside the subscriber's scope; never another agent's capability chain or full view.
* Read-your-writes and snapshot reads by `WalSeq` stay as specified in `docs/SCHEMA_AND_CONSISTENCY.md` section 3.

### 5.8 Agent identity and capabilities (N7)

* Identity stays Ed25519 `did:key`.
* Grants become **delegation chains**: the repository authority issues a root grant; a holder can issue a narrower grant to another key. Each link may only narrow: operations (`Read`, `Propose`, `Evaluate`, `Review`, `Publish`, `Undo`), path prefixes, reference scope (own drafts only; canonical only through the promotion queue), change scope, quotas (request rate, storage, and footprint), and expiry [S21, S22]. Each link signs the parent link's digest, the `repo_id`, the audience DID, and its caveats. Rate and size quotas are partitioned: the children of one grant together never exceed it. The server accepts a chain only if every link is unexpired and unrevoked at the request's `WalSeq`. Revocation is an operation in the log and cannot be undone.
* **Change scope.** A grant can name the `ChangeId`s its holder may join (section 5.1); joining a `ChangeId` outside the holder's creating chain needs it, and pruning other attempts needs a chain that is or dominates the creating chain.
* **Footprint breadth is charged.** Declaring a footprint costs the declarer: each declared path prefix, weighted by the number of tracked paths beneath it, is charged against the grant's quota for as long as the draft or subscription stays open. A footprint of the whole repository is allowed but costs the most, so one agent cannot subscribe to everything for free and make every operation fan out to it.
* Every admitted mutation is signed: an agent mutation keeps its agent's Ed25519 signature (threat model T1 and T3), and a server-derived revision carries the server machine key's `DerivationAttestation` naming its inputs and rule (section 5.1). Nothing is admitted unsigned, and no derived revision claims an agent's signature it does not have. Verification runs on all cores before the single writer (section 5.9), so it is off the serial path; batch verification is experiment X2.

### 5.9 Storage and scale (N9)

* **Group commit** (W1, Phase 5 item 1, in flight on `feat/phase5-group-commit`): one device flush acknowledges every change in the batch, durable before acknowledgement. W1 measures the storage bound on this host; this ADR uses its results and does not repeat them.
* **Log-structured segments instead of a file per blob:** WAL records and content chunks are appended to the same segment files, so a batch is one sequential write plus one flush, with no per-object files, per-object directory flushes, or partly filled filesystem blocks. An in-memory index maps digest to (segment, offset) and is rebuilt from checkpoints.
* **Durability contract:** a change is acknowledged only after `fdatasync` of its segment returns success, and after a directory flush whenever a new segment file was created. Whether the device's flush survives power loss (the drive's volatile write cache) is a device property that experiment X0 and W1 must establish; until then it is UNVERIFIED and the guarantee is stated as "survives process crash and kernel crash".
* **Binary canonical encoding** replaces `serde_json` for WAL payloads and checkpoints (`crates/synapse-store/src/lib.rs` lines 829, 984, 1148, 1292 today), so replay stops parsing text.
* **Parallel stages, one serial point:** signature verification, hashing, and merge computation run on all cores before the writer; the single writer per repository only appends and updates the index, which keeps one total order per repository.
* **Content-defined chunking** for blobs above a threshold (experiment X6); the wire sends only chunks the receiver lacks (FindMissingBlobs style [S14]).
* **Retention is per owner, not per log position.** Today the store keeps a changeset while `now_ms - created_at_ms <= default_retention_window_ms` (default 3,600,000 ms, a client-supplied time) or while `lease_expires_at_ms > now_ms` (`checkpoint_and_compact` in `crates/synapse-store/src/lib.rs`). Counting retention in `WalSeq` instead would let one agent that floods writes push everyone else's work out of the window, breaking P6. The v2 rule: an owner's revisions, operations, and views are retained while that owner's grant (`expires_at_ms` in `synapse-auth`) or any lease it holds is live, and for a policy window in server-clock seconds after the later of the two; inside that, each owner is limited by a storage quota partitioned down its delegation chain (section 5.8). An owner whose quota is full gets a typed refusal for new writes until it frees space; nothing of any other owner is evicted to make room.
* **Discards that free space.** A plain discard is an ordinary operation: it stays undoable inside the owner's window and the work keeps counting against the quota, since undo never deletes. A **final discard** is the owner's explicit choice to give up undo for its own work. Only a key in the owner's chain, or one that dominates it, may issue it, and it cannot be undone. From that operation the work stops counting against the owner's quota, and it becomes collectable at the next garbage collection unless another root still reaches it (canonical lineage, a revision of another owner that names it as parent, a receipt the cache can serve, an open change group, or a view inside another owner's undo window). Work kept alive by another root is charged to nobody's quota until that root releases it. P6 holds because only the owner's own action ends its work, so a quota-full owner can always free space without waiting for its grant to expire. The storage quota is a resource limit, not a performance measure.
* **Garbage collection** from roots: canonical lineage, owner retention (above), the per-owner undo window, the inputs and outputs of receipts the action cache can still serve, and the members of open change groups. Obsolete revisions stay restorable until their owner's undo window ends (ADR 0002 cutover gate 3, history-safe GC). The root rule for GitHub pull request projections is removed with the legacy adapters (section 5.11).
* **Scale-out:** the repository is the unit of total order. More throughput comes from moving the bound (group commit, segments, parallel stages), and more repositories from more writers.
* **Change groups across repositories (N13):** a `ChangeGroup` record names one revision per repository. Repositories that share change groups also share a **group manifest**: one record mapping each `repo_id` to its canonical `TreeDigest`, and the canonical head of each member repository is read from it. A group is tested as one action whose composite input root names every member tree (section 5.1), so a receipt can show that `omega` builds against the exact `physics` tree it will land with. The group promotes by one compare-and-swap on the group manifest, from the current manifest digest to one that moves every member at once, carrying each member repository's delegate threshold over the group payload. Either every member lands or none does, so there are no compensating reverts, no window in which the repositories disagree, and no separate quorum for a revert. The cost is that canonical moves of linked repositories pass through one serial point, the manifest writer; drafts and proposals stay per repository. PR L1 measures that serial point in seconds and joules per group.

### 5.10 The minimal Git bridge (machine interop only)

* **Import:** full history into native objects, with a persistent `GitOid` to (`ChangesetId`, `TreeDigest`) map; merge parents, tags, modes, and signatures preserved (signatures as opaque data).
* **Export:** deterministic materialization (existing, `git fsck` clean) written as packfiles, not loose objects; thin packs on the wire.
* **Remote helper:** `git-remote-synapse` (ADR 0002 Phase 6).
* Imported commits keep their original Git commit and tag headers as opaque bridge data, so exporting imported history reproduces the same Git object IDs, except where content was erased (below).
* **Erased content and the bridge.** Native identities do not change on erasure: the `BlobDigest` stays, so `TreeDigest`s, `ChangesetId`s, and receipts over imported or canonical history remain verifiable (section 5.13). Git object IDs cannot survive it, because Git hashes the bytes. A commit whose tree reaches an erased blob, and every descendant of it, therefore exports as a **rewritten projection**: the erased blob is replaced by a deterministic placeholder blob naming the signed erasure record's digest, and the new Git object IDs are recorded in the map beside the original ones, which are kept as data and never exported again. The identical-ID guarantee of PR H1 holds only for history with no erasure; this break is deliberate and documented. The Radicle check (section 5.5) is then made against the projection's `GitOid`: the delegates must sign the rewritten projection head, and until the threshold has signed it, promotion through the Git edge is refused as split-brain (`SplitBrainDivergence`), failing closed.
* Native revisions exported to Git need a message and author fields because Git requires them. They are generated deterministically from the `IntentRecord` and the agent's DID; they are a format requirement, not text for humans.
* The bridge never confers promotion authority (unchanged).

### 5.11 What is dropped as human-only

* **Removed from the native model:** prose commit messages; author names and e-mail; wall-clock time inside identity; the staging area; working-tree checkout as the default; blame and log display; interactive rebase; human branch naming; review comments and markdown; PR titles and bodies.
* **Legacy edge adapters, removed after agent cutover (Phase 8), as ADR 0002 section 2.4 already states:** `GitHubPullRequestProjection` and `project_github_pull_request` with its markdown body; `advance_human_branch_fast_forward` and `RefusalCode::GitRefNonFastForward` (the human-branch guard); the garbage-collection root rule that keeps changesets referenced by GitHub pull request projections (`docs/SCHEMA_AND_CONSISTENCY.md` section 4.1 item 2, and the `github_projections` loop in `checkpoint_and_compact`; a rule in code, not a type, since `GarbageRoot` appears only in documents and comments); the `WalRecord::GitProjected` record kind (kept readable for replay of old logs).

### 5.12 End state: Omega on AIENOS, talking to the metal

The end-state stack is: agent, then Synapse binary frames over shared memory, then the Synapse core written in Omega, then the AIENOS kernel, then NVMe and the CPU's hash and signature instructions, with no foreign runtime and no filesystem in between. The Rust crates and their conformance suites (WAL, Git, Radicle, plus the suites added in section 9) are the specification-by-test that the Omega port must pass byte for byte.

### 5.13 Leaked secrets (N15)

* **Scan at admission.** Every blob, intent `context` blob, and receipt log is scanned for secrets (key and token formats, high-entropy strings in assignment positions) on the parallel stages before the single writer. A hit refuses the admission with a typed refusal, so the secret never reaches the log, the index, or the cache. The scanner's rule set is versioned data, and its seconds and joules per accepted change are reported like any other layer (section 6.3); it stays only while it justifies its cost.
* **Audited cryptographic erasure, the only exception to P6.** Scanning misses some secrets. Content is therefore stored encrypted under per-object data keys held in a key table outside the content segments; destroying a key makes every copy of that content unreadable, including copies in old segments and backups. Erasure is an operation that needs the delegate threshold, names the `BlobDigest` (or chunk) erased and the reason class, and cannot be undone. Its effects: the key is destroyed; trigram index postings for that content are removed; action-cache entries whose inputs or outputs include it stop being served; context traces that reference it are erased with it. The digest stays, so history remains verifiable and a later read returns a typed "erased" result, never different bytes. Its effect on Git export and the Radicle check is stated in section 5.10.
* **The layer must pay its way.** Per-object encryption sits on the hot path. Experiment X9 measures its seconds and joules per accepted change and compares it with the alternative of physically rewriting segments at compaction to drop the erased bytes; the cheaper method that still reaches every copy, including backups, is kept.

## 6. Performance: Chasing the Physical Bound

### 6.1 The metrics

* **Seconds per accepted change:** the latency distribution (p50, p99, maximum) from request sent to durable acknowledgement, and the steady-state interval between acknowledgements under load.
* **Joules per accepted change:** energy counter difference over the run divided by accepted changes, reported with and without the idle baseline subtracted.
* **Watts:** mean and peak over the run.
* Each is reported with its bound and the fraction of the bound achieved. Agent counts are measurement points only.

### 6.2 The bounds and their inputs

| Bound | Derivation | Input and source |
| :--- | :--- | :--- |
| Durable latency for one change | one device flush of one sequential append, plus the change's bytes moved once at memory bandwidth | Flush time and device bandwidth: W1's measurement on this host (Phase 5 item 1). Memory bandwidth: A0 (not yet measured) |
| Steady state per accepted change | the largest of: flush time divided by batch size; bytes per change divided by device write bandwidth; bytes touched per change divided by memory bandwidth; cryptographic work per change divided by all-core throughput | W1 (flush, device bandwidth); A0 (memory bandwidth, all-core throughput of SHA-256 and Ed25519 verification on every core at once) |
| Read of n bytes | n divided by memory bandwidth, plus one index lookup | Memory bandwidth: A0 (not yet measured) |
| WAL replay | the largest of: bytes that must be read divided by device read bandwidth (memory bandwidth when they are already in the page cache, as in Gate 4); bytes that must be digested divided by all-core hashing throughput | Gate 4 section 8: replay re-reads and re-digests every committed blob, so the bytes are its "Store bytes (apparent)" column, 117,196,023 bytes at 10,000 changesets (WAL plus 14,957 blob files), against a 344.575 ms median `SynapseStore::open` with a warm page cache. A0 (`docs/A0_HOST_BOUNDS.md`): bound 5.267 ms, the hashing term at the all-core SHA-256 implementation reference (the memory term at the published 273 GB/s is 0.429 ms); fraction of bound reached = 0.0153 (bound 5.267 ms, measured 344.575 ms, 65.4 times the bound). **Superseded by J3** ([`docs/J3_CRYPTO_REFERENCE.md`](../J3_CRYPTO_REFERENCE.md)): the all-core SHA-256 reference is now 39.46 GB/s (the `sha2` crate on the SHA-2 instructions), so the bound is 2.970 ms (calc:d25d95ec) and fraction of bound reached = 0.00862 (bound 2.970 ms, measured 344.575 ms, 116 times the bound) (calc:a8960c47, calc:4cffeef5) |
| Thermodynamic reference | Landauer: at least kT ln 2 joules per bit erased [S26] | 2.871e-21 J per bit at 300 K (calc:b9494dee). **Bounds come from the hardware, not from one implementation.** A bound must hold for any implementation, so it is derived from device flush time and bandwidth, memory bandwidth, and throughput with every core working, never from one library on one core. A single-core rate measures one implementation: a parallel replay, or a replay using BLAKE3, could beat it, which would put the "fraction of bound" above 1 and make it meaningless. Where the hardware gives no closed-form limit for a computation (Ed25519 verification has none here), the input is the best all-core throughput of any available implementation, labelled an implementation reference rather than physics; if a later measurement beats it, the reference is replaced by that measurement, so the fraction stays at most 1 by definition.

**Single-core reference rates (supporting facts, not bounds).** Ed25519 verify: 42.07 microseconds per signature on one core (calc:20f50860, converted from the OpenSSL count). SHA-256: 2.458 GB/s on one core for 16 KiB blocks, so 4.86 microseconds for an 11,949-byte change (calc:8bc3db27). At that one-core rate the 117,196,023 replay bytes would take 47.69 ms (calc:1382b220); this is a figure for one implementation on one core, not a bound, so no replay fraction is stated until A0. Host probes for these rates (single runs, raw output not sealed, so provisional until PR A0 repeats them with sealed evidence): OpenSSL 3.0.13, `taskset -c 9 openssl speed -seconds 2 -evp sha256` and `taskset -c 9 openssl speed -seconds 2 ed25519`, on core 9 (Cortex-X925, 3.9 GHz maximum), host load average 2.74 at the time. OpenSSL reported `OPENSSL_armcap=0xfd`, and the CPU lists the `sha2` feature, so these rates use the hardware SHA-2 instructions.

**Energy instrument.** The host exposes the `aien_spbm` hwmon device (hwmon3 on 2026-10-14) with energy channels `pkg`, `cpu_e`, `cpu_p`, `gpc_unverified` (always 0), and `gpm`, in microjoules per the kernel hwmon interface [S27]. Per the Omega energy protocol as summarised in the Turing unit brief: 10 Hz sampling, 1 mJ step, a 32-bit counter that wraps near 4.29 MJ, and no external calibration, so absolute accuracy is not claimed. Synapse energy figures reuse Omega's energy preflight discipline (refuse with `INSTRUMENT_UNAVAILABLE` rather than substitute) and are labelled provisional until that instrument is calibrated.

## 7. A Level 0 Turing-Unit Proposal: How Well the Change Representation Describes Code History

Performance stays in seconds, joules, and watts (section 6). The Turing unit fits a different question: how well Synapse's change representation predicts real code history. This section is **Level 0 (definition only)**. No result is claimed; energy is provisional. It is not a performance measure: P3 and section 6 govern performance, and no turing or turing-per-joule figure may stand in for seconds, joules, or watts.

**Validation level, stated plainly.** Level 0: the unit is the owner's proposal, defined here and not yet computed on any Synapse data. Its definition was taken from the Turing unit brief's summary of the preprint, not checked against the preprint text for this ADR. No one has independently recomputed it, and its energy input waits on an uncalibrated instrument. Moving above Level 0 needs, in order: one figure computed under a sealed profile (below), an independent recomputation from the sealed data alone, and a calibrated energy instrument before any yield is reported.

**The unit.** 1 turing (T) is one bit of net held-out description-length saving against a declared baseline, after charging the model's own size: T = [L(B) + L(D|B)] - [L(M) + L(D|M)], in bits. Turing yield is T per joule and exists only when joules are measured. (Definition from the preprint "Computing Machinery and Understanding", live copy at aienos.com/research/computing-machinery-and-understanding, as summarised in the Turing unit brief of 2026-10-14. "T" is also the SI symbol for tesla, so the unit is written "turing (T)" at first use.)

**Prediction task.** Observations D are the held-out sequence of tree transitions of real AIEN repositories: for each held-out commit in first-parent order, the resulting repository tree given every earlier tree. Each observation must be reconstructed byte for byte; L(D|M) is the code length in bits of M's lossless encoding of D given the training history (equivalently, the sum of -log2 p_M over the observations).

**Model M.** Synapse's representation and coder for the same transitions: structured and semantic deltas (path, region, and syntax-tree edit scripts), content-defined chunks, and deduplication against all earlier history. L(M) is the size in bits of everything needed to decode: the decoder artifact and all fixed tables, including every tree-sitter grammar the semantic tiers use, so semantic merging pays for its parsers.

**Baseline B.** Git's own delta coding of the same history: thin packs (`git pack-objects --thin --stdout`) of each held-out commit against the training history, with the Git version and every pack option (window, depth, compression level) fixed in the profile. L(B) is charged with the same rule as L(M) (the decoder artifact needed to read the pack).

**Held-out split.** A chronological cut per repository, fixed before any coder is tuned: training is history up to the cut; held-out is everything after it. The held-out commit list and tree digests are sealed (hash recorded, contents blinded from whoever tunes M) and audited for overlap (no held-out tree, or cherry-pick of one, present in training).

**Measurement profile (fixed and versioned before the data is seen).** Baseline and its options; the encoding rule for L(M) and L(B); quantizer (none: lossless code lengths, whole bytes times 8); the split, seal hash, and blinding; the energy instrument (`aien_spbm` `pkg` channel, 10 Hz, 1 mJ step, idle-subtracted, with the attribution rule I_AB = E_AB - E_A - E_B + E_0 when anything else runs); the uncertainty method (per-observation distribution and a resampling interval over held-out commits); the shared-background record; and the overlap audit. Numbers compare only within one profile and are not comparable to any Omega Turing-yield figure.

**Yield.** Turing yield = T divided by the idle-subtracted joules of encoding and decoding the held-out split with M, once the energy instrument meets its calibration level; until then any T per joule figure is labelled provisional.

## 10. Rejected Ideas and the Independent Review

### 10.1 Top rejections

1. **Line-graph patch storage (Pijul, Darcs) as the native store:** evidence must name a concrete tree, and reads must not rebuild a graph; the algebra is kept without the storage.

## 11. Consequences

* Agents stop doing checkouts, rebases, and repeated identical test runs; the server rebases a draft lazily when it is next used, the action cache returns repeated results (and says `Flaky` when runs disagree), and builds read inputs by digest where possible.
* Every performance claim becomes a fraction of a physical bound with open data; there are no headline multipliers.
* Envelope v2 changes `ChangesetId` semantics (content only); v1 records stay readable through a versioned migration.
* The design adds state (operation views, markers, receipts, footprints, admission witnesses, derivation attestations, change groups, the group manifest, data keys) that the cutover gates of ADR 0002 section 4 must cover: backup and restore, repair, history-safe GC, bounded memory.
* Independent re-execution for promotion costs energy: each required action runs as many times as the policy demands (by default the delegate threshold). Those joules are reported per accepted change, so the price of trust is measured rather than hidden.
* Keeping one agent signature per mutation puts a floor of one Ed25519 verification per accepted change on the CPU budget; it runs on all cores off the serial path, and X2 measures whether batching lowers it.
* Retention becomes a per-owner budget: an agent that writes too much is refused its own further writes instead of pushing out anyone else's work.
* Linked repositories trade some independence for atomic landing: their canonical moves pass through one manifest writer, whose seconds and joules per group are measured in L1.
* Erasable storage adds work on the hot path (per-object keys or segment rewrites); X9 decides the method by seconds and joules, and erasure is the only way anything an agent produced is destroyed.
